# 插件平台是怎么运作的

这篇文档讲平台内部的实现原理，不是写插件必须看的东西——照着 `student_manual.md` 的步骤做就能完成作业，不需要看这篇。这里是给想搞清楚"这套机制到底是怎么跑起来的"的同学看的，Python 版和 C 版原理不一样，分开讲。

## 要解决的问题

每次实验都要加一个新算法进平台，而且不能每加一个就去改平台的核心代码——核心代码和算法代码必须是两件事。这就是"插件化"：核心程序只认一个统一的接口（Python 是 `Plugin` 类，C 是 `PluginInfo` 结构体），具体是哪个算法、怎么实现，核心程序完全不关心。

接下来两节分别讲 Python 和 C 怎么做到"新增一个文件，核心代码一行都不用改"。

## Python 版：运行时扫描 + 动态导入

`main.py` 里的 `load_plugins()` 做了三件事，对应 `plugins/` 目录下的每一个子文件夹：

1. **找文件**：用 `Path.iterdir()` 遍历 `plugins/` 下的每个子目录，检查里面有没有 `plugin.py`。

2. **把它当模块导入**：正常的 `import` 语句要求模块名在代码里写死，没法用在"不知道有多少个、叫什么名字"的场景。这里用的是 `importlib.util.spec_from_file_location` + `module_from_spec` + `exec_module`，效果等价于把这个 `.py` 文件当场读进来执行一遍，但模块名是运行时拼出来的字符串（`plugin_<目录名>`），不需要提前知道。

3. **把类找出来**：模块执行完之后，用 `inspect.getmembers(module, inspect.isclass)` 拿到这个模块里定义的所有类，筛选出"继承了 `Plugin`、但不是 `Plugin` 本身"的那些，实例化、塞进一个列表里返回。

这三步决定了插件文件必须长什么样：文件名必须是 `plugin.py`（第 1 步按这个名字找），里面至少要有一个继承 `Plugin` 的类（第 3 步按这个条件筛）。只要满足这两点，`category`、`name` 叫什么、`run()` 里写了什么，平台完全不关心——这就是"统一接口"的意思：平台认的是"这是不是一个 `Plugin`"，不认"这个 `Plugin` 具体是什么算法"。

新增一个插件之所以不用改 `main.py`，是因为第 1 步的 `iterdir()` 每次启动都会重新扫一遍磁盘上实际有什么文件夹，而不是读一份写死的名单。

## C 版：编译时静态注册

C 没有运行时 `import` 这种东西，`plugins/` 下的每个 `.c` 文件是在**编译阶段**就和核心代码一起变成同一个可执行文件的（见 `Makefile` 里的 `$(wildcard plugins/*/*.c)`，新增目录后这一行会自动把新文件纳入编译列表，不用手动改）。

问题是：编译进同一个可执行文件之后，程序怎么知道"这里有几个插件、分别是谁"？`main()` 里没有一行代码去调用任何一个具体的插件文件，核心代码压根不知道插件文件的存在。

答案是每个插件文件自己主动"举手报到"，靠这段代码：

```c
static void __attribute__((constructor)) register_self(void) {
    plugin_register(&info);
}
```

`__attribute__((constructor))` 是 GCC/Clang 提供的一个特殊标记，意思是"这个函数不需要被任何人调用，程序一启动、`main()` 还没开始跑之前，运行时会自动执行它"。所以即使 `main.c` 里完全没提到某个插件文件，只要这个文件被编译进了最终的可执行文件，它的 `register_self` 就会在 `main()` 跑之前自动执行一次，把自己的 `PluginInfo` 塞进 `plugin_registry.c` 维护的那个全局数组里。等 `main()` 真正开始跑、调用 `menu_ui_run()` 的时候，所有插件早就注册完了。

这和很多 C 程序用 `dlopen`/`dlsym` 在**运行时**动态加载 `.so` 文件的做法不一样——那种做法的好处是不用重新编译核心程序就能换插件，但代价是要维护一套 ABI 版本兼容机制（新增字段要考虑旧插件会不会崩），Windows 下也没有 `dlopen` 这个函数，得额外写一层兼容代码。对这门课来说，"每次都重新编译一次"的成本几乎为零（代码量很小，编译几秒钟），换来的是不用碰 ABI 版本、不用管 Windows 兼容性，这笔账划算。所以 C 版选的是编译时静态注册，不是运行时动态加载。

## 两版本的共同点：接口即契约

不管哪个版本，核心代码（`app.py`/`menu_ui.c`）真正依赖的只有接口里的几个固定字段：`name`、`category`、`description`、以及"能被调用来执行"这件事（Python 是 `run(text, vis)` 方法，C 是 `run` 函数指针）。核心代码只按这几个字段编程，不知道也不关心任何一个具体插件内部在干什么——这就是"接口"的意义：它是双方的一份约定，核心代码照着约定去读插件的信息、调用插件，插件照着约定去实现，两边互不需要知道对方的实现细节。

想验证自己理解了，可以试着回答：如果同一个插件文件里定义了两个都继承 `Plugin` 的类，Python 版会发生什么？（提示：看 `load_plugins()` 里那个 `for` 循环。）
